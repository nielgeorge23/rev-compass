RevCompass · Consolidated System Architecture

RevCompass converts claim-level variances into evidence-backed recovery cohorts

Deterministic analytics identify patterns, Gemini-powered agents investigate and recommend, and humans approve before action. RevCompass sits above your existing EHR / RCM system of record — it does not replace it.

Variance taxonomy — "variance type" is broader than "denial type"
  • Contractual adjustment — expected, rules-based reduction per an active vendor contract; only treated as a variance worth working if no active contract explains it.
  • Denial — payer refused payment; carries CARC/RARC.
  • Write-off — no further recovery path; terminal disposition.
  • True underpayment — paid below the contracted rate with no denial code; evaluated against fee-schedule terms, not CARC/RARC.
A single claim can carry multiple CARC/RARC codes — the primary code (highest dollar impact) drives classification; secondary codes stay on the record as evidence but don't split the claim across cohorts. An active-contract check runs first to separate contractual adjustments from true variances.
Classification degrees
  • 1st degree: payer + denial / variance category.
  • 2nd degree: CPT/DRG family + service line.
  • 3rd degree: location + variance-amount band.
Timely-filing deadline is not a classification factor — two claims that match on the factors above belong in the same cohort even if their filing windows differ. Filing deadline only sets action urgency downstream.

Guardrail — clustering identifies a pattern; it does not prove root cause. Deterministic signature matching and analytics-driven cohorting run first (payer × CARC/RARC × CPT/DRG family × variance band); Gemini may only merge or split a candidate cohort when independent evidence spans converge on the same clause — never on narrative similarity alone. The root-cause hypothesis only emerges downstream, after evidence and reasoning are applied.
Confidence, ambiguity & priority at the cohort stage
  • Each candidate cohort carries its own cohesion confidence — how tightly its member claims actually match — separate from the disposition confidence scored later.
  • Ambiguous claims (ones that could plausibly belong to two cohorts) route to a human-in-the-loop grouping decision before any downstream reasoning is spent on them.
  • Cohort priority is ranked by dollar exposure first, timely-filing urgency second.
Naming: a group of claims is a cohort — the unit that's clustered, enriched, decided and tracked as one. A package is the claim-level artifact produced on approval and filed with the payer (one appeal or resubmission per claim).
L4

RevCompass Intelligence Core

5

RevCompass Intelligence Core

per-engagement · siloed

Each cohort flows through the capabilities in a defined sequence — the Orchestrator sets which capabilities are active for a given variance pattern, but the order is fixed. Variance amounts are consumed from upstream, never re-retrieved or recalculated here.

Capability sequence per cohort — to confirm with Shaun
  • 1. Root-cause identification — form a hypothesis (e.g. for underpayments, a candidate explanation a user can manually verify).
  • 2. Next-best-action reasoning — the responsible agent works the hypothesis toward a resolution path.
  • 3. Payer pattern detection — check the hypothesis against this client's payer behavior history.
  • 4. Disposition decision — based on the above, decide appeal / write-off / resubmit for the cohort; if appeal, produce the claim-level packages for filing.
No variance retrieval or recalculation happens in this core — that is already computed upstream in the Signature Layer and consumed as-is.
ENGINE
A business capability — Payer Behavior, Denial Disposition, or Contract Variance.
AGENT
A specialized AI worker executing part of an engine's capability.
TOOL
A deterministic calculation or retrieval step — no LLM reasoning involved.
COHORT / PACKAGE
The cohort is the action-ready unit — claims, exposure, evidence, hypothesis, action, confidence. A package is the per-claim artifact it produces for filing.
Orchestrator Agent — ADK supervisor · cohort identified → evaluates variance type → activates relevant capabilities, run in the fixed sequence above · variance never re-derived here

The three engines are the capabilities in that sequence — Contract Variance does root-cause for underpayments (step 1), Payer Behavior does pattern detection (step 3), Denial Disposition makes the call (step 4). Every cohort runs the sequence; which engines light up depends on its variance type.

🔒 Payer Intelligence — built from this client's own historical data

Payer fingerprints are built per engagement from the client's own history. Payer-level intelligence draws on:

  • This client's historical appeal / recovery outcomes
  • This client's remit history and denial/underpayment patterns
  • Published payer policies and public regulatory / transparency sources
Each client's fingerprint and overturn-rate tables are siloed to that client. There is no pooling of behavior across clients.
Failure & fallback (reasoning core)
  • No evidence span above the similarity threshold → "insufficient evidence," the cohort routes to manual research, never auto-recommended.
  • Gemini call times out or errors → one retry with backoff; second failure routes the cohort to manual review with the error logged, not silently dropped.
  • Contract exceeds context window in one pass → chunked retrieval fallback rather than truncation.

It's decided once, as a unit — then, on approval, it produces the claim-level packages actually filed with the payer (one appeal or resubmission per claim).

Every cohort runs the fixed capability sequence; within it, the Orchestrator activates only the engines a given variance pattern needs (e.g. Contract Variance stays off when there is no underpayment question).
From cohort to work — assignment, drafting & Epic sync
  • Manual team assignment — each cohort can be routed to the right team (e.g. Appeals Filing, Coding, Scheduling/Auth); the assigned team is shown on the cohort.
  • Appeal Package Drafter — when the action is appeal, drafts the letter from a repository of payer-specific appeal templates, surfacing the best-fit template for the analyst to edit before submission.
  • Workqueue & Epic sync — an approved cohort's packages become tasks in the owning team's existing workqueue and sync back into Epic, so RevCompass never becomes a second system to check separately.

L7

Outcome & Learning

7

Action & Outcome

Built · hackathon MVP
event-driven

Appeal / resubmission packages

The approved cohort produces one filing package per claim, submitted to the payer or RCM system of record.

Per-claim outcome capture

Payer response splits back to claim level — a cohort rarely resolves uniformly.

→ Feeds Payer Fingerprint

Confirms or dampens the drift signal that triggered the cohort.

→ Feeds Overturn-Rate Table

Updates p(overturn) for this payer × reason × action going forward.

→ Re-opens Clustering

A claim that resolves differently from its cohort majority is flagged as possibly mis-grouped.

→ Prevent ticket

Internal root causes (auth workflow, coding) route into the owning team's existing queue — not a new inbox. Closes when drift reverses.

The loop closes here: outcomes recalibrate the confidence formula, the fingerprint, and — when a claim breaks pattern — the clustering itself.
🛡

Security & Guardrails

Model Armor

Prompt-injection defense on ingested contract/policy PDFs — untrusted text is wrapped in a fixed delimiter the model is instructed never to treat as instructions; directive-sounding spans are excluded from evidence.

IAM & access control

Analyst / Supervisor / Director roles with distinct permissions — Director is read-only across all cohorts, with no approve, assign, or draft actions.

Full audit log

Every cohort logs its evidence snapshot, model version, tool outputs, and the named approver — frozen at decision time, not reconstructed after the fact.

BAA + de-identification

Production runs under a BAA with de-identification and a HIPAA-configured Vertex AI deployment.
